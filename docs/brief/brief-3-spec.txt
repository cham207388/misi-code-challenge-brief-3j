 VA MISI Technical Challenge - Mock Build Brief 3 (Revised)
 Memorial Event Operations & Permit Case Management | Multi-module full-stack practice exercise | October 2026

 Fictional exercise. This is not a VA-issued specification. Use invented cemeteries, employees, applicants, records and documents.
 The system must have multiple independently usable pages, not one dashboard with tabs or placeholder buttons.


 1. Challenge objective
 Build an internal case-management web application that receives event applications, checks eligibility and schedule availability,
 reserves cemetery spaces and resources, routes applications for review, issues permits, coordinates day-of-event operations,
 records incidents and generates management reports. The application must be fully functional from login to final case closure.
 Use local/developer-controlled environments. Git version control, repeatable setup and automated tests required.

 6. Detailed functional requirements and integration
 FR-01 Authentication. Local login/logout, authorization policies and role-aware navigation; seeded demo credentials in README
 only.
 FR-02 Applications. Create, autosave, reopen, edit and submit across four wizard steps. Prevent duplicate submits.
 FR-03 Register. 20 rows per page, server sorting and search, filters, export; deep links maintain filters.
 FR-04 Reviews. Eligibility checklist with required documents; information requests with due dates and historical responses.
 FR-05 Calendar. Real persisted reservations displayed in monthly, weekly and daily views; drag/drop optional, not required.
 FR-06 Conflict engine. Reject time overlaps incl. buffers, blackouts, capacity and reservation of identical resources.
 FR-07 Resources. Track available inventory by site/date/time and release allocations on cancellation.
 FR-08 Approvals. Approve/reject with reviewer/approver separation and timestamped decision history.
 FR-09 Permit PDF. Server-generated downloadable PDF containing permit reference, venue/time, conditions and verifiable token.
 FR-10 Check-in. Staff can validate permit token via typed code/QR payload and record check-in/check-out idempotently.
 FR-11 Incidents. Incident creation, photo attachment, follow-up owner, due date, severity and resolution audit.
 FR-12 Notifications. Mock email gateway with sent/failed statuses, retry button and an outbox; no live email required.
 FR-13 Reports. Calculated KPIs from database, date filters, chart drilldowns and CSV; not hard-coded demo totals.

 7.1 Integration contracts and implementation guards
 Registry verification: response contains referenceId, matchedName, eligibilityStatus (Valid/Flagged/Unknown), verifiedAt. A
 Flagged or Unknown result prevents eligibility pass until reviewer records an override permitted by explicit rules; each check
 generates an audit record. Request retries must use bounded exponential backoff only for transient errors; 404 is not retryable.
 Calendar integration: token endpoint returns access_token, expires_in and token_type; calendar events have externalId,
 venueCode, startUtc, endUtc, modifiedUtc. Cache tokens server-side, renew before expiry, store lastSyncCursor; dedupe by
 externalId. If external calendar is down, local tentative reservation may remain but final approval is blocked until reconciliation
 succeeds.
 Gateway webhook: delivery callbacks include eventId, messageId, status (Delivered/Failed), occurredAtUtc, signature and
 timestamp headers. Reject invalid signatures (401), replay outside 5-minute tolerance (401), and process duplicates idempotently
 (200). Keep full status transitions and never regress Delivered to an earlier status. Use outbox + background worker for sending, not
 inline permit issuance.
 Object storage: server validates extension, MIME and magic bytes, max 5 MB; generate random object keys, use private buckets,
 and record checksum, uploader and audit events. Allow a short-lived signed download URL only after role validation; expired links
 and unauthorized access must fail. Provide local MinIO in Compose so no paid cloud account is needed.

 Weather: display source timestamp, forecast details and clear Severe Weather advisory markers. Cache for 15 minutes; service
 timeout shows previously cached data labelled Stale, never a fabricated live forecast. Severe warnings require Manager
 acknowledgment before permit issuance, but do not silently cancel a case.
 CSV/SFTP: use an optional Docker SFTP container or an equivalent local mock drop directory (documented as an SFTP
 simulation). Data feed columns: partnerEventId, siteCode, startUtc, endUtc, attendeeCount, updatedAtUtc. Reject malformed rows
 with a downloadable error report; repeat import should not duplicate events. Save batch ID, checksum, counts, last completed sync
 and mapping diagnostics.
 Geocoding: return candidates with label, latitude, longitude and confidence (0-1). If two candidates tie, require user selection;
 persist lat/long only after confirmation. API unavailable means the venue editor remains usable and flags the coordinates as
 unverified. A map widget may use a local/static tile dataset; internet access is not mandatory.

 7.2 External integration administration and visible screens
 The eight additional routed pages (19-26) are mandatory. Integration Hub supports per-service healthy/degraded/offline states and
 masked configuration display; never show secret values. Each integration-specific page must contain working live service results,
 last-request time, meaningful empty/error states and testable actions. Expose an Integration Attempt detail drawer or route with
 request ID, sanitized HTTP response code, timing, retry attempt and linked case ID.

 7.3 Failure matrix to demonstrate

    Scenario                                Expected observable behavior


    Registry returns 429                    Respect Retry-After or bounded delay; reviewer sees pending verification; never pass without evidence.


    OAuth token expires                     Renew token and replay once; on invalid_client show admin actionable error without secret leakage.


    Calendar 409 conflict                   Do not finalize; show source event, slot alternatives and reconciliation history.


    Webhook duplicates/forgery              Accept one genuine delivery event only; reject incorrect HMAC; keep immutable attempt log.


    Storage link expires                    403/expired message and a role-authorized regenerate-link action; protected object remains private.


    Weather timeout                         Use explicitly stale cached result if present; do not block viewing case or crash page.


    CSV contains bad rows                   Import valid rows per documented partial-success policy; produce per-row errors; safe re-import.


    Geocoder ambiguous/offline              Prompt for selection or manual unverified address; no invented GPS coordinates.


 7.4 Security and local environment requirements
 Use HTTPS where configured, API-key secret management, OAuth2 client credentials (no real secrets), webhook HMAC
 verification with constant-time comparison, least-privilege storage access, scheduled jobs with locking, circuit-breaker/timeouts
 where appropriate, correlation IDs and structured error handling. Services must run locally in Docker Compose or processes
 documented in README. Seed a service scenario panel or environment switches to simulate success, slow responses, 401, 404,
 409, 429, 500, callback duplicates and outages. Never hardcode provider keys or require real accounts.


 8. Acceptance tests specific to integrations
 Automated: contract tests for each external adapter; unit tests for credential/token handling, deduplication, retry classifications,
 HMAC and cache expiration; integration tests for storage access, failed webhook verification, 409 calendar conflict and malformed
 CSV; browser tests for each of pages 19-26. Record mock API call counts to prove the UI makes real requests. All external failures
 must have user-visible recovery and produce traceable logs.
 Required live demo extension: verify applicant through API-key registry; resolve an OAuth calendar conflict; send a notification
 and receive signed delivery webhook; download a PDF using expiring object-storage link; view cached weather when forecast API is
 offline; ingest partner CSV with some bad rows; select a venue geocode candidate; open Integration Hub and inspect the correlated
 failure logs.

 10. Technical delivery and acceptance criteria
 Preferred: ASP.NET Core .NET 8 with Blazor or MVC, EF Core, PostgreSQL in Docker Compose, ASP.NET Core Identity, xUnit,
 Playwright, structured JSON logs, separate mock APIs for registry, calendar, notification, forecast and geocoding; MinIO, mock
 SFTP/CSV feed. Different stack allowed if documented and independently runnable. Git (not GitHub) is required.
 Acceptance: every page has distinct route/navigation entry; working persistence; no dead controls, lorem ipsum blocks or
 decorative-only charts; validation on client and server; meaningful error states; responsive polished layouts on desktop/mobile;
 clean-machine install, migrate, seed, run and test commands; no secrets in Git. Screen recordings or snapshots do not replace
 runnable features.
 Submission: complete repository, README with demo accounts + architecture + environment setup, data model/ERD, workflow
 diagram, API spec, automated test report, sample screenshots of all 26 pages, including integration screens, implementation log
 and known limitations.
 Pass/fail: auto-generated application that only includes a dashboard, forms, static cards or non-functional placeholders fails. At
 least 26 routed pages and the complete multi-role demonstrated journey must work end-to-end.
